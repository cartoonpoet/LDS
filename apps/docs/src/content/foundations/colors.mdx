<h2 id="semantic-palette">시맨틱 컬러 구조</h2>

LDS는 raw color를 직접 쓰는 대신, **foundation → semantic → component** 순서로 색 체계를 올립니다.

- foundation: `bluePalette[500]`, `grayPalette[300]`
- semantic: `semanticColorRoles.text.primary`, `semanticColorRoles.action.primary.hover`
- component-domain: `semanticColorRoles.button.solid.primary.background`, `semanticColorRoles.field.borderFocus`

<h2 id="semantic-domains">현재 semantic domain</h2>

현재 UI-v3 기준으로 아래 역할이 정리되어 있습니다.

- `surface`
- `text`
- `border`
- `action`
- `status`
- `button`
- `field`
- `badge`
- `chip`
- `alert`

이 구조 덕분에 컴포넌트 CSS에서 raw hex를 반복하지 않고, 같은 상태 의미를 여러 컴포넌트가 공유할 수 있습니다.

<h2 id="state-mapping">상태 매핑 원칙</h2>

Zeplin의 상태 시안은 semantic token으로 먼저 흡수합니다.

예:
- Primary Button / Hover → `semanticColorRoles.button.solid.primary.hover`
- Input / Focus Border → `semanticColorRoles.field.borderFocus`
- Error Field / Focus Ring → `semanticColorRoles.status.danger.fill`
- Info Alert / Background → `semanticColorRoles.alert.info.background`

<Callout>
  같은 색상이라도 의미가 다르면 다른 token으로 분리하는 편이 유지보수에 유리합니다. 예를 들어 버튼 hover blue와 focus ring blue는 우연히 같을 수 있어도 역할은 다릅니다.
</Callout>

<h2 id="consumer-customization">서비스별 커스터마이징</h2>

서비스에서는 컴포넌트 CSS를 직접 덮어쓰기보다, 토큰 런타임 헬퍼를 통해 테마 변수를 재정의하는 방식을 권장합니다.

- 브랜드 메인 컬러 변경
- 상태색 미세 조정
- 다크 테마 준비용 alias 치환

<Callout>
  브랜드 색상 변경은 토큰 레이어에서 처리해야 상태색, 보더, 포커스 링까지 함께 정합성을 유지할 수 있습니다.
</Callout>

<h2 id="usage-guidance">사용 가이드</h2>

- 주요 CTA는 `action` / `button` token을 통해 일관되게 강조합니다.
- 폼 컴포넌트는 `field` + `status` token 조합으로 상태를 표현합니다.
- badge / chip / alert는 컴포넌트 전용 semantic domain을 우선 사용합니다.
- foundation palette는 semantic token을 설계할 때만 직접 참조하고, 앱/컴포넌트에서 바로 소비하는 것은 최소화합니다.
